# 학생·수업·보고서 저장 구조 전환

## 학원 계정·강사 가입 요청 (2026-09-21)

- 앞선 마이그레이션에 이어 `migrations/202609210002_academy_join_requests.sql` 전체를 SQL Editor에서 실행하고 프런트엔드를 배포합니다. 기존 학원과 소속 사용자는 그대로 유지됩니다.
- Google로 로그인한 뒤 아직 소속 학원이 없는 계정에만 학원/강사 선택 화면을 표시합니다. 학원 계정은 학원을 생성하며, 강사 계정은 학원 이름(두 글자 이상)으로 검색해 가입을 요청합니다. 검색 결과에는 이름과 식별번호만 표시됩니다.
- 운영자는 설정 → 강사 가입 요청에서 이메일과 이름을 확인하고 승인/거절합니다. 강사는 승인 상태 확인 버튼 또는 페이지 새로고침으로 결과를 확인합니다. 자동 반복 조회는 하지 않습니다.
- 승인된 강사는 `staff`로 소속되며 학원 운영자와 같은 학생·반·보고서·오답·인수인계 편집 권한을 가집니다. 가입 요청 승인/거절은 운영자(`owner`)만 가능합니다.
- 승인 전에는 학원 업무 데이터에 접근할 수 없습니다. 요청자나 다른 학원 운영자는 요청을 승인할 수 없으며, 계정당 소속 학원 하나/대기 요청 하나만 허용합니다. 대기 요청 취소, 거절 후 재요청이 가능합니다.

## 저장 충돌과 PostgREST 재시도 수정 (2026-09-21)

- SQL Editor에서 `migrations/202609210001_non_retryable_conflicts.sql` 전체를 실행합니다. 기존 인증/워크스페이스 마이그레이션 적용 후 실행하며, 데이터와 권한은 유지합니다.
- 이 마이그레이션은 보고서·수업·오답의 업무상 충돌 코드를 `40001`에서 `PT409`로 변경합니다. PostgREST 14에서 같은 요청을 계속 재시도하는 문제를 막으며 버전 검사와 전체 배치 롤백은 유지합니다.
- 프런트엔드도 함께 배포합니다. `PT409`를 충돌 안내로 처리하고, 선택만 한 기존 보고서는 저장 대상에서 제외합니다. 수정 후 선택 해제한 학생과 선택한 새 보고서는 계속 저장됩니다.
- 이미 재시도 중인 요청은 마이그레이션만으로 종료된다고 보장할 수 없습니다. 호출 수가 계속 증가하면 작업을 멈추고 프로젝트 재시작 후 확인합니다.
- 검증: 서로 다른 반을 같은 시점에 불러와 각각 저장하면 모두 성공해야 합니다. 같은 보고서를 두 창에서 수정하면 나중 요청은 HTTP 409 한 번으로 종료되고, 초안과 미저장 표시가 유지되며 저장 중 표시가 해제돼야 합니다.
- 로컬 테스트는 DB 오류 코드/원자성과 화면 저장 범위를 검증합니다. 운영 PostgREST의 실제 응답과 CPU 안정 여부는 SQL 적용 후 별도로 확인해야 합니다.

## 로컬 개발과 배포 환경

- `npm run dev`는 `.env.local`에 Supabase 키가 있어도 IndexedDB만 사용합니다. Supabase 클라이언트를 초기화하거나 서버 데이터를 읽지 않습니다.
- `npm run build` 후 `npm start`도 localhost/127.x/IPv6 루프백/사설 IP/`.local` 주소로 접속하면 IndexedDB를 사용합니다.
- Vercel 등 공개 주소의 프로덕션 빌드는 Supabase를 사용합니다. 배포 환경에는 Supabase 환경 변수와 아래 SQL 적용이 필요합니다.
- 로컬 DB 이름은 `cosmath-local-v1`이며 반·학생·수업·보고서를 각각 보관합니다. 처음에는 빈 상태입니다.
- 로컬 데이터는 같은 브라우저와 같은 출처(주소·포트)에서 유지됩니다. 브라우저 사이트 데이터를 삭제하면 함께 삭제됩니다. 운영 DB와 자동 동기화하거나 이관하지 않습니다.
- 로컬에서도 버전 충돌 검사와 원자적 배치 저장을 사용합니다. IndexedDB 사용이 차단되면 오류를 표시하며 Supabase로 우회하지 않습니다.
- `npm run backup:legacy`는 명시적으로 운영 Supabase 백업을 요청하는 별도 관리자용 스크립트이며 앱의 로컬 저장 모드와는 별개입니다.

## 적용 순서

1. 기존 앱의 편집을 잠시 멈추고 열린 보고서 화면의 변경사항을 저장합니다.
2. Supabase 프로젝트 SQL Editor에서 `migrations/202609140001_normalized_reports.sql` 전체를 실행합니다. 루트의 `supabase_schema.sql`도 같은 내용입니다.
3. 아래 검증 쿼리로 백업과 이관 결과를 확인합니다.
4. 새 앱을 배포하고 기존 창을 모두 새로고침합니다.
5. 학생 등록, 날짜별 보고서 저장·재조회, 퇴원 후 기존 보고서 조회를 확인합니다.

현재 프로젝트에는 URL과 anon key만 있습니다. 이 키로 테이블이나 함수를 생성할 수 없으므로 SQL Editor의 관리자 실행이 필요합니다. 앱은 테이블 생성 전에는 오류를 표시하고 쓰기를 차단하며, 구 JSON 저장 방식으로 돌아가지 않습니다.

## 데이터 보존과 기본값 제거

- 코드에 있던 학생 명단과 초기화 기능은 제거했습니다. 새 DB에는 반과 학생을 자동 생성하지 않습니다.
- 이관 대상은 **현재 `cosmath_settings`에 저장된 데이터**뿐입니다. DB 학생이 예전 기본 학생과 같은 이름이라는 이유로 삭제하지 않습니다.
- 원본 세 키는 `cosmath_legacy_backup`에 복사하고 원본 테이블에도 그대로 남깁니다. 백업은 일반 앱에서 접근할 수 없습니다.
- 중복 학생 ID 또는 잘못된 JSON은 마이그레이션 전체를 중단합니다. 전체 명단 초기화나 임의 병합을 하지 않습니다.
- 목록에서 이미 삭제됐지만 개별 수정 내용이 남아 있는 학생은 `이관된 과거 기록` 반의 비활성 학생으로 보존합니다.
- 과거 저장 방식에는 보고서 작성 여부/날짜별 이력이 없었습니다. 따라서 현재 공통 내용과 개별 수정 내용을 합친 스냅샷을 이관합니다. 실제 작성·발송 이력을 뜻하지 않습니다.
- 이관 날짜는 기존 공통 데이터의 `date`에서 추출하며, 날짜가 없으면 이관 당일(한국 시간)을 사용합니다. 개별 보고서의 표시 날짜는 원문을 보존합니다. 이미 사라진 과거 이력은 복원하지 않습니다.

## 저장 규칙

- `cosmath_classes`: 반 한 개당 한 행.
- `cosmath_students`: 학생 한 명당 한 행. 삭제 버튼은 `active=false`로 퇴원 처리합니다. 물리 삭제 권한은 앱에 없습니다.
- `cosmath_lessons`: 반 + 날짜당 한 행. 현재 화면 기준 하루 한 수업이며 정규/보충은 보고서 내용입니다. 같은 날 여러 회차 분리는 별도 확장이 필요합니다.
- `cosmath_reports`: 수업 + 학생당 한 행. 이름, 학년, 반, 보고서 내용은 당시 스냅샷으로 보관합니다.
- 일괄 편집은 선택한 학생에게만 적용합니다. 공통 수업 내용은 이후 새 보고서의 기본값으로 사용하며 기존 스냅샷을 소급 변경하지 않습니다.
- 저장 버튼은 선택한 새 보고서 및 변경된 보고서를 저장합니다. 선택 해제된 학생의 미저장 수정도 함께 저장됩니다.
- 학생 등록·퇴원은 즉시 요청하고 성공 후 화면에 반영합니다. 조회만으로 저장하지 않습니다.
- 보고서 저장 RPC는 버전을 비교하며, 수업·보고서 전체 배치를 하나의 트랜잭션으로 처리합니다. 충돌 시 일부만 저장되지 않으며 작성 내용은 화면에 유지됩니다.
- 이관 후 기존 세 JSON 키에는 DB 트리거로 쓰기를 차단합니다. 이전 앱의 열린 창은 새 저장 구조에 영향을 주지 못합니다.

## 검증 쿼리 (관리자 SQL Editor)

```sql
select key, source_updated_at, backed_up_at from public.cosmath_legacy_backup;
select * from public.cosmath_migrations;
select count(*) as classes from public.cosmath_classes;
select active, count(*) from public.cosmath_students group by active;
select report_date, count(*) from public.cosmath_lessons group by report_date order by report_date;
select count(*) as reports from public.cosmath_reports;
```

## 로그인과 학원 워크스페이스 적용

`202609170001_auth_workspaces.sql`은 Google 로그인과 학원별 데이터 격리를 위한 후속 마이그레이션입니다.

1. 기존 마이그레이션 세 개를 먼저 적용합니다.
2. 운영 화면의 편집을 잠시 멈추고 `202609170001_auth_workspaces.sql`을 SQL Editor에서 실행합니다.
3. Supabase Dashboard의 Authentication > URL Configuration에서 배포 주소를 Site URL로 설정합니다.
4. Redirect URLs에 배포 주소와 개발 주소(예: `http://localhost:3000/**`)를 추가합니다.
5. Google Cloud에서 OAuth 2.0 Web client를 만들고 Supabase Dashboard에 표시되는 callback URL을 Authorized redirect URI로 등록합니다.
6. Google Client ID와 Client Secret을 Supabase Authentication > Providers > Google에 입력하고 활성화합니다.
7. 앱에 가장 먼저 로그인해 학원 이름을 입력합니다. 이 최초 계정이 기존 데이터를 인수하는 `owner`가 됩니다.

인증 마이그레이션을 이미 적용했다면 바로 이어서 `202609170002_remove_ambiguous_foreign_keys.sql`도 실행합니다. 학원 격리용 복합 외래키와 기존 외래키가 동시에 노출되어 PostgREST 관계 조회가 모호해지는 것을 방지하는 후속 마이그레이션입니다.

프로필 사진 업로드를 사용하려면 `202609170003_profile_avatars.sql`을 추가로 실행합니다. 이 마이그레이션은 2MB 이하 JPG, PNG, WebP 파일을 저장하는 공개 아바타 버킷과 사용자별 쓰기 정책을 생성합니다.

새 마이그레이션은 기존 반, 학생, 수업, 보고서, 오답, 인수인계를 삭제하지 않습니다. 소유자가 없는 임시 학원에 먼저 귀속한 뒤 최초 워크스페이스 생성자가 인수합니다. 따라서 마이그레이션 적용 후 공개 주소를 다른 사람에게 전달하기 전에 실제 소유자 계정으로 먼저 로그인해야 합니다.

적용 후 `anon`의 업무 데이터 권한은 제거됩니다. 로그인한 사용자도 `academy_members`에 등록된 자신의 학원 데이터만 RLS와 RPC 검증을 통과할 수 있습니다. 현재는 사용자당 학원 한 곳과 `owner` 역할만 실제 UI에서 사용하며, `staff` 역할은 향후 초대 기능을 위해 예약되어 있습니다.

마이그레이션은 트랜잭션으로 실행됩니다. 실패하면 `ROLLBACK;` 후 원인을 확인하고 재실행합니다. 성공 후 재실행은 데이터를 다시 이관하지 않습니다. 되돌릴 경우 새 테이블에 작성한 데이터를 먼저 별도 보존해야 하므로 기존 테이블이나 백업을 임의 삭제하지 마세요.
